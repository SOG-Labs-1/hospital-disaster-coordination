# 設計書：院内災害対応ツール

作成：2026-11-04（Claude Code ハッカソン 2026 期間中）
表記：【確定】依頼者の意向として決定済み ／ 【提案】Claudeの提案で依頼者が了承 ／ 【未決定】実装しながら決める

## 1. 目的と優先順位

院内調整本部が「誰が・どこに・どんな状態で、何を依頼し、何が実行されたか」を確認時刻つきで共有できる実務ツールを作る。同じ設定と画面で、Claude APIを相手に一人でも調整を練習できる訓練モードを備える。

1. 【確定】実際の院内災害対応で役立つ管理・調整の仕組み（最優先）
2. 【確定】各病院の構成や指示系統に合わせられる設定
3. 【確定】同じ仕組みを使ったAI訓練モード

- 【確定】患者の状態と所在の把握が中心。搬送管理だけのツールにしない
- 【確定】「指示したこと」と「実行されたこと」、「未確認」と「0件」を区別する
- 【確定】試作品が動くことと、実災害で安全に使えることは分ける（§12 検証事項）
- 【確定】AIは診断・トリアージ判定・治療判断を行わない。実運用モードではAIを使わない
- 応募テーマ：テーマ1「あなたにしかない深さを」。看護師として院内BCP訓練で見えた課題が出発点

## 3. 設計の基本方針

すべての操作を「記録（クロノロジー）」として追記し、画面の状態は記録から集計する。これで、訂正履歴・監査記録・同時編集の検知・訓練の振り返りの根拠が1つの仕組みでそろう。

### 3.1 イベント（記録）の共通項目

| 項目 | 内容 |
| --- | --- |
| id | 連番またはULID |
| type | イベントの種類（§3.3） |
| subject | 対象（患者、搬送、要請、場所、搬送要員など）の種類とID |
| payload | 種類ごとの中身 |
| reportedBy | 報告元（役職・場所・人） |
| enteredBy | 入力者 |
| terminal | 入力した端末（場所） |
| observedAt | 現場で確認した時刻（入力時に変更可、既定は入力時刻） |
| recordedAt | サーバーが記録した時刻 |
| corrects | 訂正の場合、訂正対象のイベントID |
| override | 警告を承知で実行した場合の警告コードと理由 |
| mode | `live`（実運用）／`training`（訓練）。保存先ファイルも別 |

### 3.2 コマンドとイベントの流れ【提案】

1. 画面がコマンドを送る（`POST /api/commands`、対象の `expectedVersion` つき）
2. サーバーがドメインロジックで検証する
   - 版番号が古い → 競合として返す（画面は差分を見せて選ばせる）
   - 重複・超過などの警告 → 警告として返す（画面は理由を選ばせて再送）
3. 問題なければイベントを追記し、Server-Sent Eventsで全端末に配信する
4. 各端末は `shared/` の集計ロジックで状態を更新する

### 3.3 イベントの種類（初期案）

- 患者：`PatientRegistered` `PatientIdentifierAdded` `PatientTriageChanged` `PatientNoteUpdated` `PatientsMerged`
- 場所：`LocationStatusReported`（受け入れ可否・区分別の受け入れ可能人数）`StaffCountReported` `ZoneAssignmentChanged` `RouteNoteUpdated`
- 体制：`PositionAssigned`（役職への人の割り当て）`DeputyAssigned`
- 搬送（調整）：`TransportRequested` `TransportAccepted` `TransportDeclined` `TransportDirectedByHQ` `TransportStaffAssigned` `TransportOrdered` `TransportAcknowledged` `TransportCancelled` `TransportRedirected`
- 搬送（事実）：`TransportDeparted` `TransportArrived`（引き渡しを含む）
- 搬送要員：`TransporterRegistered` `TransporterAvailabilityChanged`
- 支援要請：`SupportRequested` `SupportAssigned` `SupportDispatched` `SupportReceived` `SupportCompleted` `SupportCancelled`
- 共通：`EventCorrected` `MessageLogged`（無線・電話の連絡メモ）

### 3.4 未確認と0

- 数値は `{ value: number | null, confirmedAt: string | null }` で持つ。null は「未確認」と表示する
- 確認から一定時間（病院設定、【未決定】初期値）を過ぎた情報には「古い」印を付ける

## 4. 病院設定（`config/hospitals/*.yaml`）

| 設定項目 | 内容 |
| --- | --- |
| 場所 | id、名前、種類（病棟・救急外来・手術室など）、端末の有無 |
| 災害時の用途 | 赤・黄・緑・黒ゾーンなど。用途と場所の対応（複数可、開始時刻つき） |
| 受け入れ能力 | 場所ごと・区分ごとの初期値 |
| 役職と権限 | 本部長、ゾーン責任者、搬送調整担当、患者の所在把握担当など。各役職ができる操作 |
| 受け入れ了承の権限 | 既定：判断は場所の責任者と代行者、入力は誰でも（判断者と入力者を両方記録）。「場所の担当者なら誰でも」にも切り替え可 |
| 搬送の段階 | 各段階の必須／省略、担当役職、到着と引き渡しを分けるか |
| 搬送要員と班 | 搬送要員（1人ずつ）、よく組む班 |
| 資源 | ストレッチャー、車いす、酸素ボンベなど |
| 確認項目 | 病院のBCPチェックリスト。訓練の振り返りで照合する |
| 職種 | 医師、看護師、搬送要員、事務など |
| 警告の理由 | 定型の選択肢 |
| 古い情報の閾値 | 分 |

- 【確定】搬送本部は必須にしない。本部が兼任する構成も専任担当がいる構成も、役職と権限で表す
- デモ用に2つの架空病院を用意する
  - 病院A（架空「Claude総合病院(仮)」。当初の「さくら総合病院」は同名の病院が実在することが分かったため変更）：救急外来＝赤ゾーン、外来ホール＝黄、講堂＝緑、リハビリ室＝黒、手術室、病棟3つ、本部に専任の搬送調整担当
  - 病院B（架空「Hackathon中央病院(仮)」、小規模）：外来処置室＝赤、待合＝黄・緑、本部が搬送調整を兼任、病棟2つ、手術室1つ
  - 【未決定】具体的な数値は実装時に決める

## 5. 患者

- 【確定】システムが短い管理番号を自動発行し、内部IDとする
- 【確定】タッグ番号は手書きなので重複・読み違いがあり得る。唯一のIDにしない
- 【確定】入院患者はベッド番号で識別しない。リストバンドの院内患者IDを使うが、病院による違いや、緊急時に作れない場合がある
- 【提案】予備の識別に、災害診療記録のメディカルID（西暦生年月日8桁＋性別＋カタカナ氏名の先頭7文字）を入力できる
- 【提案】同じタッグ番号・院内IDの登録は警告し、「既存の患者を開く」か「理由を書いて別人として登録」を選ぶ
- 【提案】同一人物と分かった記録は統合でき、統合も記録する
- 【提案】画面では管理番号またはタッグ番号の末尾を大きく表示し、性別・推定年齢・服装などの特徴メモを必ず並べる

| 保持する情報 | 内容 |
| --- | --- |
| 識別 | 管理番号（自動）、タッグ番号、院内患者ID、メディカルID、氏名（不明可）、性別、推定年齢、特徴メモ |
| トリアージ区分 | 履歴つき |
| 所在 | 物理的にいる場所。搬送中は「搬送中（出発元→到着先）」 |
| 担当部署 | 責任を持つ部署。到着時に所在と一緒に移る |
| 状態メモ | 主な状態、必要な処置、付き添いの要否（搬送判断のための最小限の共有情報） |
| 自由メモ | 任意 |

## 6. 搬送

```
調整・指示（依頼したこと）：搬送要請 → 受け入れ了承 → 要員の割り当て → 指示・受領確認
事実（起きたこと）　　　　：出発 → 到着（引き渡し） → 要員は自動で待機へ
```

- 【確定】要請は現場からも本部からも出せる。搬送の指示を出すのは本部（本部内の搬送調整担当を含む）
- 【確定】到着と引き渡しは1つの記録。到着時に所在と担当部署が到着先へ移る。分けたい病院向けに設定で切り替え可能（提案）
- 【確定】調整が未記録でも出発・到着は記録できる。欠けた確認は「未記録」として本部画面と振り返りに出す
- 【確定】到着後、搬送要員は自動で「待機」へ。【提案】位置は最後の到着先。休憩や機材補充のときは1クリックで「対応不可」
- 【確定】搬送中の患者は独立した一覧で「赤ゾーン→手術室」のように確認できる
- 【確定】付き添い（職種と人数）と搬送手段（独歩・車いす・ストレッチャー・担架）を搬送ごとに記録。付き添い中は元の部署の人数に「うち付き添いで不在」と表示
- 【提案】受け入れ側が準備できず待っている状況は到着時のメモで残す
- 【提案】中止・行き先変更はどの段階からでも可能。理由を記録

| 重複・矛盾 | 扱い |
| --- | --- |
| 同じ患者への2件目の搬送指示 | 警告。理由を記録すれば実行可 |
| 稼働中の搬送要員・班への割り当て | 警告。理由を記録すれば実行可 |
| 受け入れ可能人数を超える了承 | 警告。理由を記録すれば実行可 |
| 出発の記録がないままの到着 | 到着は記録し、「出発未記録」と表示 |

## 7. 支援要請

1. 要請（部署または本部。種類は人員・物品・その他）
2. 本部が受付（担当者が付く）
3. 手配の指示（誰に・何を・どこへ）
4. 到着・受け取り（要請した側が記録。端末のない部署は本部が無線で聞いて代わりに入力）
5. 完了

- 【確定】要請が実行されたかどうかが分かるようにする
- 【提案】担当が付かないまま、または指示後に「届いた」記録がないまま一定時間が過ぎた要請は「未対応」「未完了」として目立たせる

## 8. 人員・搬送要員・資源

| 対象 | 管理の単位 |
| --- | --- |
| 場所ごとの人員 | 職種別の人数、確認時刻つき【確定】 |
| 搬送要員 | 1人ずつ（名前または「搬送A1」のような呼び名）【確定】 |
| 搬送班 | よく組む搬送要員の組み合わせ。まとめて割り当て可能【確定】 |
| 付き添い | 搬送ごとの職種と人数【確定】 |
| 資源 | 種類ごとの数量、確認時刻つき【提案】 |

- 【確定】1回の搬送に1人以上を割り当てられる。個人単位でも班単位でも動かせる
- 【提案】搬送要員の状態：待機・割当済・移動中・対応不可
- 【確定】経路管理（エレベーター停止など）は範囲外。場所ごとに「経路の注意」の自由記述欄だけ用意

| 本部PC | 院内全体／患者一覧／搬送／要請・連絡／クロノロジー（初期案、試作を見て見直す） | マウス |

| 各部署PC | 自部署の患者・受け入れ状況・人員。届いた要請と了承依頼を上部に固定表示 | マウス |
| 訓練の操作パネル | シナリオ開始・一時停止・2倍速、部署役への連絡、振り返り | マウス |

- 端末は場所に紐付け、操作ごとのログインはしない。入力者は名前一覧から1クリックで選ぶ
- 【確定】一覧にない入力者は、フルネーム・職種（必須）と職員番号（任意）で追加する。場所はその端末の場所（いま働いている場所）を使い、普段の所属部署は聞かない（この一覧は誰が入力・報告したかの記録に使い、人員は場所ごとの人数で管理するため）

- 宛先が端末のない場所の要請・指示は、調整担当の画面に「無線で伝達が必要」と出す
- 院内全体の画面に「確認が古い・未確認の情報」の一覧を置く（情報整理を促すため）
- 印刷：患者一覧、搬送中一覧、要請一覧、場所の状況。白黒で判別でき、出力日時・確認時刻・実運用／訓練を表示
- フォント BIZ UDゴシック、本文18px以上、ボタン48px以上、WCAG 2.2 AA、状態は色＋文字＋形

## 10. AI訓練モード

ホワイトボード型の机上訓練（Emergo Train Systemなど）を電子化し、他部署の役を「対抗役（カウンタープレイ）」としてClaudeが担う。参加者は実運用と同じ画面を使う。

### 10.1 構成

```
シナリオ（YAML） → シミュレーター（真の状態・時間・出来事）
                      ↓ 部署ごとに知り得る情報だけ
                   AI部署役（提案だけを出す。strict tool use）
                      ↓ 検証
                   シミュレーターに反映 ／ 本部への連絡メッセージとして届く
参加者（本部役） → 同じ実務画面に、連絡を聞いて自分で入力（＝訓練用の記録）
```

- 【確定】人数、所在、受け入れ能力、資源、搬送状態、時間、イベント条件はシミュレーターが管理する
- 【確定】各部署のAIには、その部署が知り得る情報だけを渡す
- 【提案】AI部署役からの報告は、参加者のボード（記録）を自動では更新しない。参加者が聞いて入力する。これが情報共有の訓練になる
- 【提案】シミュレーターの「真の状態」と参加者の「ボード」は別に持つ。ずれが振り返りの根拠になる
- 【提案】AI部署役の行動（例：`reply_message` `report_status` `accept_transport` `decline_transport` `request_support` `report_departure` `report_arrival`）はスキーマで固定し、シミュレーターが検証する（存在しない患者の報告、能力を超えた了承などは不可）
- 【確定】架空患者・出来事の生成は、条件と整合性確認を通して反映する
- 【提案】識別の訓練として、同じ番号の手書きタッグが2枚あるなどの出来事を混ぜる
- 【確定】初期版の参加者の役は本部。他の役は将来
- 【確定】時間は実時間が基本。一時停止と2倍速。デモは15分程度のシナリオを早送り

### 10.2 振り返り

点数や順位でなく、記録と確認項目（病院のBCPチェックリスト＋シナリオの確認項目）を照合して示す。AIは根拠となる記録（イベントID）を示して説明する。

1. 情報が確認・共有されなかった箇所（真の状態とボードのずれ）
2. 要請に担当が付かなかった箇所
3. 指示の受領や実行が確認できなかった箇所
4. 受け入れや引き渡しの調整が途切れた箇所
5. 担当や手順がそもそも決まっていなかった箇所

- 【確定】「記録がない」と「実施しなかった」を区別し、参加者が画面外の対応や判断理由を補足できる
- 照合そのものはプログラムで行い、AIは説明文を作る役に限る【提案】
